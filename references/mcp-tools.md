# 麦当劳 MCP 调用规范与踩坑记录

本文件记录的都是**实测验证过**的行为，不是文档抄写。全部测试环境：
门店 `storeCode=3390023`（麦当劳衡阳船山餐厅），`beType=1`、`orderType=1`，2026-10-10。

## 接入

```
url     : https://mcp.mcd.cn
type    : streamableHttp
headers : { "Authorization": "Bearer ${MCD_MCP_TOKEN}" }
```

- 传输协议 **Streamable HTTP**。
- 每个 Token 每分钟最多 **600 次请求**，超了返回 `429`。
- `401` = Token 无效/过期/未带。
- 每次规划通常 3~8 次调用，离配额很远，不要为穷举而打满。

## beType / orderType 矩阵

| 场景 | `beType` | `orderType` | 是否传 `beCode` |
|---|---|---|---|
| 到店自取 | 1 | 1 | **不传**（传了会报错） |
| 得来速车道取餐 | 5 | 1 | 必传，来自 `query-nearby-stores` |
| 麦乐送到家 | 2 | 2 | 必传，来自 `delivery-query-stores` |
| 企业团餐 | 6 | 2 | 必传，来自 `delivery-query-stores` |

## 坑 1：`query-meals` 不传 beCode ≠ 可以传空串

`beType=1` 时后端返回的门店**根本没有 `beCode` 字段**。此时给下游工具传 `beCode` 会直接报错。拿到什么就传什么，别自己补默认值。

## 坑 2：菜单里是有价格的

`query-meals` 的每项都返回 `currentPrice` 与 `originalPrice`，**单位是元**（字符串）。
不需要靠 `calculate-price` 反推价格——先在本地按价格筛，再用 `calculate-price` 核价，是正确且省配额的顺序。

## 坑 3：`calculate-price` 返回的单位是分

`price` / `discount` / `productPrice` / `productList[].subtotal` 全部是**分**。
`price: 8740` 要展示成 `87.40`。漏除 100 会把价格写成 100 倍。

## 坑 4：套餐选配必须用 `roundList`，且这是解决忌口的关键

含轮次的餐品（随心配、三件套、双人分享餐…）在 `calculate-price` 里必须用 `items[].roundList` 指定每一轮选了什么：

```jsonc
{
  "productCode": "9900013304",
  "quantity": 1,
  "roundList": [
    { "round": "1", "comboItemList": [{ "code": "1450", "quantity": 1 }] },
    { "round": "2", "comboItemList": [{ "code": "3050", "quantity": 1 }] }
  ]
}
```

实测：四份不同选配的随心配分别算出 13.90 / 14.90 / 14.90 / 13.90，与 `query-meal-detail` 里的 `diffPrice` 完全一致。

**为什么这件事很关键**：`随心配` 的蓝区（主食）有 8 个官方候选，其中包含麦香鱼、双层吉士汉堡（不辣）和麦香鸡、麦乐鸡（鸡肉）。不吃辣的人和想吃鸡的人，**各自都能从官方候选里合法地挑到**，不需要靠关键词去猜一份套餐里到底有什么。

## 坑 5：套餐里常有"隐藏的便宜选项"

`巨无霸三件套`（¥37.5）的小食轮里，`小杯玉米杯` 的 `diffPrice` 是 `- ¥1`，比默认的中薯条还便宜。引擎会自动选它，于是实际 36.5。

对比一下就知道差距有多大：
- 巨无霸单品 ¥26.5 + 脆脆薯条 ¥16 + 可乐 ¥9.5 = **¥52.0**
- 巨无霸三件套（选小杯玉米杯）= **¥36.5**

**便宜 15.5 元。** 所以"极致省钱"策略必须优先套餐，不能拿裸单品拼。

## 坑 6：不是所有分享餐都能给忌口的人吃

`全明星双人分享餐八件套`（¥49.9）的第 1 轮"选择汉堡"只有两个候选：
`麦辣鸡腿汉堡` 和 `酥酥多笋卷`——**两个都是辣的**。

所以对明确不吃辣的人，这份 ¥49.9 的分享餐**整个不可用**。引擎的做法是：若任一必选轮次没有合法候选，直接放弃整份餐品，退到下一款，绝不把辣餐端上去。

## 坑 7：`query-my-coupons` 不等于"这张券能用"

- `query-my-coupons` 返回卡包里的券，官方描述明确写了：**不进行门店、渠道、配送方式等下单规则校验，不承诺可用于当前订单**。
- 判断"当前门店能用哪些券"，只能用 `query-store-coupons`。

实测：该门店 `query-store-coupons` 在 2026-10-10 返回 `data: []`——当天一张券都没有。卡包里 13 张券全部按日期生效（中薯条买一送一、王牌小食拼都要 10/12~10/16，其余 9.9 元早餐券绑定各自日期且仅限 05:00-10:29）。

**所以"今天有券吗"的答案是动态的**，Skill 必须现场查，不能写死，也不能拿卡包券凑数说"可以用"。

## 坑 8：没有过敏原字段

菜单 `tags` 与详情 `choices` 里**都不存在**"辣/不辣""含花生/含乳"这类结构化字段。
本项目的辣味判定是**名称与标签文本的关键词启发式**（`辣`、`川香`、`麻辣`、`黑椒`）。

- 命中 → 判为辣
- 没命中且拉过详情 → 判为不辣
- 没拉过详情 → **只能标"未知"**，不能默认不辣

README 与对外输出必须如实说明这是启发式，不构成过敏建议。

## 坑 9：`enjoyable.balance` 是凑单提示的现成数据

`calculate-price` 返回的 `enjoyable` 里有 `realDiscount`（优惠值，单位**元**）和 `balance`（门槛差额，单位**分**）。
`balance` 就是"还差多少钱才能用券"。直接展示它，比自己算阈值准。

## 官方给的团餐搭配规则

`query-meals` 的工具描述里麦当劳自己写了搭配建议，可以直接作为配餐策略依据：

- 20 元以下：小食
- 20–30 元：汉堡 + 小食，或 汉堡 + 饮料
- 30–40 元：汉堡 + 薯条/小食 + 饮料
- 40–50 元：汉堡 + 薯条 + 小食 + 饮料
- 50 元以上：丰富组合，优先不重复小食

另外 `calculate-price` 会返回 `takeWayList`（`eat-in` 堂食 / `locker-in` 外带），"堂食还是外带"这个需求 MCP 原生就支持。
