# 该拉哪些套餐详情

不是所有餐品都要拉 `query-meal-detail`——那会白烧配额。判断标准很简单：

## 必须拉

1. **名字里带"随心配""随心选""N+1"的** —— 选配空间大，不拉就不知道里面有什么。
2. **名字里带"三件套""四件套""套餐"的** —— 必选轮次里常有 `- ¥1` 的便宜选项（见 `mcp-tools.md` 坑 5），不拉就找不到。
3. **名字里带"双人餐""两人餐""分享餐""多人餐""全家桶"的** —— 轮次多且往往有 2 选 2 的轮次，是共享策略的主力。
4. **用户明确说了忌口，而你打算推荐该餐品** —— 唯有详情里的 `choices` 能证明它是否合规。

## 不用拉

- 单品（巨无霸、麦香鸡、薯条、可乐……）：没有轮次，`query-meals` 的信息已经够用。
- 甜品、饮料：同上。
- 用户完全没提忌口的场景：可以先不拉，遇到可疑项再补。

## 预算怎么算

拉 N 份详情就是 N 次调用。限额 600 次/分钟，一次拼餐规划拉 3~5 份详情完全安全。

经验做法：**先拉菜单 → 用名称筛出 3~5 个候选 → 只对这 3~5 个拉详情 → 交给引擎**。

## 引擎怎么用这份数据

拉了详情的餐品，引擎会解算每一轮的合法组合：

- 必选轮次（`minQuantity >= 1`）必须选一个
- 候选按「命中个人偏好 → 差价最小 → 默认项」排序
- 若某必选轮次**所有候选都违反忌口**，整份餐品被判为不可用（返回 `None`），这是分享餐踩雷时的兜底
- 全组撞车时，会在有限范围内改轮次，挑一个没被用过且最便宜的组合
